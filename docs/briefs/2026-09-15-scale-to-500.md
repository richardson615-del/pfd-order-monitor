## Why
Launch is ~100 tablets; the goal is 500+ restaurants within a year, i.e. roughly 8–10 new restaurants **per week**. Today, putting one restaurant live on the tablet path is a chain of manual steps across two systems (CRM onboarding record → bridge restaurant → tablet login → printer → "Turn tablet on" → test order), and problems surface as bridge health alerts by email, not as work items anyone owns. At 10/week that breaks. E1 collapses the chain into one action, E2 turns tablet/printer problems into owned trouble tickets, E3 makes sure the bridge survives 500 always-connected tablets, E4 gets 100 physical units into the system in an afternoon.

## E1 — One-click "Go live on tablet" (bridge PR `feat/crm-provision`, then CRM PR `feat/partner-go-live`)

### Facts
- CRM onboarding records carry `intake_printer / intake_app / intake_email`, `zuppler_restaurant_id`, and checklist templates for the app path (migrations 0048/0050/0074). Bridge restaurant rows are created either from the admin panel or implicitly when a printer is added (`restaurant_created` in `POST /api/crm/devices`).
- Bridge already exposes: `POST /api/crm/restaurants/:id` (patch `app_expected`, `display_mode`, branding), `GET/POST/PATCH …/logins`, `POST …/logins/print`, `POST …/test-order`. Bridge `restaurant_id` == CRM `accounts.id`.
- UNKNOWN: whether the bridge has a create-restaurant endpoint the CRM can call directly (vs. the side effect of adding a printer). Probe `app/api/crm/restaurants/route.ts` and `app/api/admin/restaurants/route.ts`.

### Build — bridge
1. `POST /api/crm/restaurants` (create/ensure, idempotent on `crm_restaurant_id`): body `{ crm_restaurant_id, name, zuppler_restaurant_id?, timezone?, app_expected?, display_mode? }` → returns the restaurant row. If a row exists, patch the provided fields and return it. Error `zuppler_id_conflict` if the Zuppler id is already bound to a different restaurant.
2. `POST /api/crm/restaurants/:id/provision` — one transaction-ish call that: ensures the restaurant is active, sets `app_expected=true`, creates a tablet login if none exists (username from `usernames.ts` rules; default = slug of the restaurant name, collision-safe), and returns `{ restaurant, login: {username, password (only when newly created)}, printers: [...], destinations }`. Audit `created` as today. Never resets an existing password.
3. Contract doc updated; pure tests for username slugging/collision and idempotency.

### Build — CRM
4. On the partner page (`/partners/[id]`) and the onboarding record: a **Go live on tablet** button (roles: admin, dispatcher, onboarding). Confirm overlay shows what will happen; on confirm the CRM calls `provision`, then:
   - if the restaurant has an active printer → offers **Print login to their printer** (existing B2 flow);
   - else → shows the one-time credential box (existing "Take this to the tablet" UI);
   - marks the onboarding checklist items for tablet provisioning (D3a) complete where the bridge result proves them (login exists; `app_expected=true`), leaves the physical steps (enrolled, alerts on) manual until D1's `tablet.online` + `push_subscribed` confirm them — then auto-completes those too on the next page load.
5. `POST /api/partners/[id]/go-live` route (thin; zod; lib `src/lib/partner-go-live.ts`; idempotent — calling twice changes nothing and returns the same state). Activity-timeline entry "Tablet provisioned by <user>".
6. Tests: route 403 for `caller`; idempotency; branch with/without active printer (bridge mocked at the `printer-bridge.ts` boundary).

Acceptance: a new partner goes from "signed" to "tablet login exists, app expected, checklist updated" in one click, under 10 seconds, with zero admin-panel visits.

## E2 — Bridge health → CRM trouble tickets (bridge PR `feat/issues-feed`, CRM PR `feat/device-tickets`)

### Facts
- Bridge `lib/health.ts` computes issues (`tablet_not_watching:<id>` critical, `restaurant_no_app_device:<id>` warning, `app_alert_failed`, printer `device_silent`, etc.) and `GET /api/crm/issues` returns `{checked_at, counts, issues[]}` with `key, severity, title, detail, first_seen_at, notified_at`. Alerts go by email/SMS webhook (`ALERT_*` env).
- CRM has dispatch tickets + notifications (migration 0077 `dispatch_tickets_and_notifications`), ticket recipients (0080), categories incl. "Hardware Issue"/`dev_issue` (0064), and `/dispatch/todo` "Trouble tickets" visible to dispatcher/tech/etc. A cron route exists (`/api/cron/sweep`).
- UNKNOWN: exact dispatch ticket schema/categories and whether a ticket can carry an external key for dedupe. Read migrations 0077/0080 and `src/lib/dispatch-log*.ts` before designing.

### Already exists (seen 2026-09-15) — extend, don't duplicate
The CRM already opens a Hardware Issue ticket from the device monitor ("Ticket failed to print: order 61642f71 … gave up after 3 attempts: ePOS code=\"EPTR_REC_EMPTY\" … Opened by the device monitor. Closes itself when the order-monitor reports it cleared.", For: Tech team, priority High). Read that code path first (`prs-crm` cron/sweep + dispatch tickets) and build E2 on top of it. Gaps observed today:
- **Stale orders get printed.** Order 61642f71 was 11 days old when the bridge tried to print it today. The Epson claim query (`app/api/print/epson/route.ts`, `.eq("status","queued").order("queued_at")`) has no age cutoff, and `queueReprint` (`lib/print-queue.ts`) resets `attempts` to 0 on any reprint. Fix in the bridge: (a) the claim query skips jobs whose order `received_at` is older than `PRINT_MAX_AGE_HOURS` (default 4) unless the job carries `manual_reprint_at` within the last 10 minutes → mark them `expired`, never `failed`, never ticketed; (b) add `print_jobs.queued_by text` (`ingest | reprint:<actor> | test | login_print`) so "why did this print?" is answerable; (c) map ePOS codes to plain English in `error` and in the CRM ticket title: `EPTR_REC_EMPTY` → "Out of paper", `EPTR_COVER_OPEN` → "Cover open", `EPTR_REC_NEAR_END` → "Paper low", schema/timeout → "Printer offline"; (d) on `EPTR_REC_EMPTY`/`EPTR_COVER_OPEN`, park the job as `held` and auto-release when the same device next polls with a clean status, cap 60 min, instead of 3 rapid retries ~5 s apart that fail before anyone could react.
- The ticket should show order age, customer, and total (from the bridge issue payload) so a tech can tell a dead 11-day-old ticket from a live dinner order at a glance, and **auto-resolve stale-order print failures** (order older than `PRINT_MAX_AGE_HOURS`) as "Expired — not needed" rather than paging the tech team.

### Build — bridge
1. Make `GET /api/crm/issues` stable for sync: every issue has a deterministic `key`, `restaurant_id` (nullable), `device_id` (nullable), `first_seen_at`, and issues that cleared since the last check appear once in a `resolved[]` array with `resolved_at` (keep 24 h of resolved keys in a small table or in-memory cache — decide from how `collectSnapshot` runs; document). Add `?since=<iso>` to return only changes.
2. Contract doc updated; tests for resolution emission.

### Build — CRM
3. Cron `GET /api/cron/device-issues` every 5 min: pull issues; for each new `key` open a dispatch ticket (category "Hardware Issue" for printers, new category `tablet_issue` via migration if the CHECK list needs it) linked to the account, with title/detail from the bridge, assigned per existing escalation rules (don't hard-code thresholds — repo rule). Store `external_key` on the ticket (migration: `dispatch_tickets.external_key text unique`) so the same issue never opens twice. When the bridge reports the key resolved → auto-resolve the ticket with note "Cleared by bridge at <time>"; if a human already closed it, do nothing.
4. Ticket UI: show a "Device" chip linking to `/devices` for that restaurant; the tablet/printer status pill from A2/D2 inline.
5. Notifications: reuse 0077/0080 recipients; critical tablet issues during business hours notify the on-shift dispatcher; outside hours, queue (respect existing quiet-hours logic if present — UNKNOWN, probe).
6. Tests: dedupe on repeated key; auto-resolve path; human-closed-stays-closed path; 403 for callers.

Acceptance: unplug a test tablet → within 5–20 minutes a trouble ticket exists on the right restaurant with the right assignee; plug it back in → ticket auto-resolves. No duplicate tickets after an hour of flapping.

## E3 — Bridge scale hardening for 500 always-on tablets (`pfd-order-monitor`, PR `chore/scale-500`)

### Facts
- Each tablet holds one Supabase Realtime channel (`orders-<restaurantId>`), polls every 60 s (15 s when not live), posts a heartbeat every 2 min, and re-syncs on visibility. Gmail poll cron runs every minute. Push fan-out iterates `push_subscriptions` per restaurant in `notifyRestaurant`.
- UNKNOWN: current Supabase plan and its Realtime concurrent-connection and messages/sec quotas; Vercel plan (function duration, cron limits); whether `orders` realtime is filtered server-side by RLS or only by client filter.

### Build
1. **Capacity sheet** `docs/scale-500.md`: measured numbers, not guesses — 500 tablets × (1 realtime connection + heartbeat every 120 s + poll every 60 s) = ~500 concurrent WS + ~12.5 req/s steady; peak ingest at dinner (estimate from the last 30 days of `orders.received_at` — query dev/prod read-only and put the p95 orders/min in the doc). Compare to the actual Supabase/Vercel plan limits (read them from the dashboards — never from memory) and state headroom or the upgrade needed.
2. **Realtime**: confirm the channel filter is enforced by RLS (a tablet must not be able to subscribe to another restaurant's orders). If RLS on `orders` is missing/loose for the anon/authenticated role, fix it in a migration. Add a **backoff + jitter** to reconnects and polls (`kiosk.ts` pure functions, tested) so 500 tablets don't stampede after a deploy or outage; the C4 idle-reload must also be jittered over 10 minutes.
3. **Heartbeat**: one upsert per restaurant is fine; add `shell_version`, `push_subscribed` if C4/D1 haven't; index `(last_seen_at)` exists — keep. Reject heartbeats faster than every 60 s per restaurant (429) to cap abuse.
4. **Push**: batch `webpush.sendNotification` with a concurrency limit (e.g. 20) and a per-restaurant cap; prune dead endpoints (already on 410/404 — keep). Confirm `notifyRestaurant` never blocks ingest (README rule: destinations don't share fate).
5. **Ingest**: verify Zuppler webhook handler is idempotent under retries at 10× current volume (existing `webhook_receipts`), and that the Gmail poller processes N restaurants within the 60 s window — add a duration log line and an alert if a run exceeds 45 s.
6. **Health checks at scale**: `collectSnapshot()` must not N+1 across 500 restaurants — single queries with joins; run time logged.
7. **Load test script** `scripts/load-500.ts` (not in `npm test`; run manually against dev): simulates 500 heartbeats + 500 polls per interval for 10 minutes and reports p95 latency and error rate. Document how to run it and the numbers observed.

Acceptance: `docs/scale-500.md` states plan limits vs. projected load with headroom %, lists any plan upgrade with cost, and the load test passes at 500 with p95 < 500 ms and 0 errors on dev.

## E4 — Bulk intake of the first 100 tablets (`prs-crm`, PR `feat/tablet-bulk-intake`, after D2)

### Facts
- D2 creates `tablets` (serial, model, asset_tag, status, account_id, mdm_device_id…) + `tablet_events`, and a 10-min MDM sync that auto-creates `stock` rows for serials the MDM reports.
- First buy ≈ 100 units of one hardware revision (candidate: ZZB ZB10, Play-certified; alternative Galaxy Tab A9). Non-zero-touch units are hand QR-enrolled.

### Build
1. **CSV import** on `/devices/tablets`: columns `serial, model, asset_tag, purchase_date, vendor, cost` → upsert by serial (status `stock`), events `received`. Report per-row errors; never partial-fail silently. Store `purchase_date`, `vendor`, `cost_cents`, `warranty_until` (migration adds columns).
2. **Asset labels**: `GET /api/tablets/labels?ids=…` → printable PDF sheet (Avery 5160-style, 30/page) with asset tag, serial, a QR encoding `crm.pfdworks.com/devices/tablets/<id>`; use `qrcode` (already a dependency) + the repo's existing PDF/print approach if any (UNKNOWN — probe; else browser print CSS).
3. **Enrolment queue view**: filter `status=stock AND mdm_device_id IS NULL` = "not yet enrolled"; once the MDM sync sees the serial, the row flips to enrolled automatically (event `enrolled`). Progress bar "73 / 100 enrolled".
4. **Ship kit** action: assign tablet → account, print the login ticket to the store's printer if online (B2) or attach the one-time credential to the ship record, generate a one-page packing slip (restaurant, asset tag, Wi-Fi hint, support number), event `shipped`.
5. Tests: CSV parser edge cases (BOM, quotes, duplicate serial in file), label PDF renders N pages, queue filter correctness.

Acceptance: import a 100-row CSV in one go, print 100 labels in ≤4 sheets, and watch the enrolment counter climb as units are QR-enrolled during the trial.
