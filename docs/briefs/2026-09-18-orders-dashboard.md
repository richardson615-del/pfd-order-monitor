## 0. Nick's intent (2026-09-18, verbatim)
"An area that shows today's orders like an order dashboard — shows the ticket information, can click and open for more information."

Who sees it: PFD staff in a browser (dispatchers, tech, accounting, admin). Not restaurants. It answers, at a glance: what orders came in today across every restaurant, which ones are sitting unaccepted or unprinted, and what exactly was on each ticket — without anyone opening the bridge's Supabase or phoning the store. **And (added 2026-09-18): each Zuppler order links straight back to that order in Zuppler's customer-service area, so staff can edit or refund it there** — the CRM shows, Zuppler edits.

## 1. Ground truth

**FACT (bridge, `pfd-order-monitor`)**
- Orders live only in the bridge's Supabase (`orders` table; columns are snake_case of `CanonicalOrderInput` in `lib/canonical.ts` L11-61: `source`, `external_id`, `restaurant_id`, `order_number`, `received_at`, `order_type`, `due_time`, `customer_name/phone/address`, `items` jsonb `{name, price, modifiers[]}[]`, money fields, `channel_id`, `payment_type`, `notes`, plus `status` (`new` → … `completed`|`cancelled`), `opened_at`, `accepted_at`, `completed_at`, `cancelled_at`, `printed_at`, `money_variance`).
- The only order-listing route the CRM can call today is `GET /api/crm/accounting/orders?from&to[&restaurant_id][&limit]` (`app/api/crm/accounting/orders/route.ts`). It was built for statements: it returns ids, status, `received_at/printed_at/cancelled_at`, restaurant, channel, order_type, payment_type and money — **no items, no customer, no notes, no due_time, no accepted_at/completed_at, no destination**, excludes `source=test`, requires `from`+`to`, and its `restaurant_id` is a plain `.eq` on the **bridge** uuid (L66) — it does *not* go through `lib/restaurant-ref.ts`, so passing a CRM `accounts.id` silently returns zero rows. It is also undocumented in `docs/crm-bridge-contract.md`.
- Every other `/api/crm/restaurants/:id/*`, `tablets/bind`, `tablets/link` accepts bridge id **or** CRM account id via `resolveRestaurantRef()` (contract §Standing rules, 2026-09-17).
- Display helpers already exist and are pure: `lib/order-display.ts` — `bucketOf()` (orders / completed / past, restaurant-local day), `isUnopened()` (NEW = `accepted_at IS NULL`), `isLate()`, `ageClass()`, `elapsedLabel()`, `itemsLine()`; `lib/kiosk.ts` `unaccepted()`; `lib/countdown.ts` (I3) for `accepted_at + prep_minutes`.
- `GET /api/crm/issues` already surfaces `order_unaccepted:<id>` (critical, 3 min after arrival) and `job_stuck/job_failed:<id>` with an `order` summary.
- `POST /api/crm/restaurants/:id/ticket-preview` renders a PNG of a **sample** ticket with the restaurant's branding; it does not take an `order_id`.
- Auth on every `/api/crm/*` route: `Authorization: Bearer <CRM_WRITE_KEY>` via `authorizeCrmWrite(req)`.

**FACT (CRM, `prs-crm`)**
- No orders page or nav item exists. Nav is `src/lib/nav-config.tsx` `NAV_GROUPS` (OPERATE group: Dispatch log, Trouble tickets, Cash log, Remakes, Drivers, Devices, Onboarding, Partners), rendered by `src/components/shell/Sidebar.tsx`; badges come only from the single `/api/nav/counts` poll keyed by nav `key` (CLAUDE.md L401-411).
- All bridge calls are server-side through `src/lib/printer-bridge.ts` and proxied under `src/app/api/printers/*` so `CRM_WRITE_KEY` never reaches the browser (CLAUDE.md L564-574). Nothing in that file fetches orders.
- Route handlers stay thin: `requireSession` → role check → zod → lib → `handleApiError` (CLAUDE.md L699-705). Page and API must share one access predicate in `src/lib/` (the `canManagePrinters()` lesson, L242-246). Adding a **role** costs six edits + a parity test (L324-338) — so reuse existing roles.
- CRM account ↔ bridge restaurant: `accounts.id` == bridge `restaurants.crm_restaurant_id`; bridge responses carry the bridge `id`. Restaurant names for display come from the CRM's `accounts`, not the bridge.

**ASSUMPTION (Nick's intent, defaults Claude Code takes)**
- "Today" = the **America/Chicago** calendar day (all PRS restaurants are Central). A date picker lets staff look back up to 30 days.
- Test orders are shown but tagged **Test** and hidden by default (toggle).
- The dashboard is read-mostly. The only actions in M2 are the ones the bridge already exposes safely: **Resend to tablet** and **Reprint** (see M1 §3). No editing of orders, no cancelling from the CRM.
- Order source (Zuppler / email / test) **is** shown to PFD staff — the "no source on the tablet" rule is about restaurants, not us.

**UNKNOWN (probe, don't guess)**
- Whether `orders` has an index on `(received_at)` alone; M1 adds one if missing (500 restaurants × a day = a few thousand rows, but the list is polled).
- Whether a "reprint" / "resend to app" primitive already exists server-side (the print-job queue has retry; check `lib/` for a re-enqueue helper before writing one). If none exists, M1 §3 is **deferred to M3** rather than invented.

## 2. Packages

### M1 — bridge: `GET /api/crm/orders` (list) and `GET /api/crm/orders/:id` (detail) — `pfd-order-monitor`, PR 1, merges first
Branch `feat/crm-orders-api`. Web-only.

1. **`GET /api/crm/orders?date=YYYY-MM-DD[&tz=America/Chicago][&restaurant_id=<bridge id | CRM account id>][&include_test=1][&since=<ISO>]`**
   - `date` required; `tz` default `America/Chicago`; the window is that local day. `restaurant_id` goes through `resolveRestaurantRef()` (either id works; 404 if neither). `include_test` default off. `since` returns only rows whose `updated_at > since` plus `{deleted:[]}` if applicable, so the CRM can poll cheaply every 20 s (same "changed since last sync" idea as E3/poll-first) — if `orders` has no `updated_at`, add it in the migration with a trigger, idempotent, in `REQUIRED_SCHEMA`.
   - Response: `{date, tz, generated_at, counts: {total, unaccepted, in_kitchen, completed, cancelled, unprinted, test}, orders: [...]}`. Each order: `order_id, order_number, source, status, restaurant {id, crm_restaurant_id, name}, received_at, opened_at, accepted_at, completed_at, cancelled_at, printed_at, due_time, order_type, payment_type, channel_id, customer {name, phone_last4}, items_line` (via `itemsLine(items, 3)`), `item_count, total` (dollars), `prep_minutes` (restaurant setting), `destinations: ("printer"|"app"|"email")[]` (via `orderDestinations()`), `print: {state: "printed"|"queued"|"failed"|"stuck"|"none", job_id?, failed_reason?}` derived from the print-job table, `flags: {unaccepted_over_3m, late, overtime}` computed with the existing helpers (`unaccepted()`, `isLate()`, countdown past zero). Sorted: unaccepted first (oldest first), then in kitchen by least time remaining, then completed/cancelled newest first — same order the tablet uses.
   - **Full phone is not in the list** (`phone_last4` only); it's in the detail.
   - Limit 2000 rows / 30 s max duration like accounting/orders; `truncated: true` beyond.
2. **`GET /api/crm/orders/:id`** → everything in the list row plus `customer {name, phone, address}`, `items[] {name, price, modifiers[]}`, `notes`, `money {subtotal, tax, service_fee, delivery_fee, tip, discount, included_tax, hidden_fee, total, variance}`, `external_id`, `zuppler_order_uuid`, `timeline[]` (`received → printed → opened → accepted → completed|cancelled` with timestamps, plus print-job attempts with outcomes), `print_jobs[]`, `app_delivery` (was it pushed to a tablet, when, which device). Never include `raw_html` / `raw_payload` — those can hold card-holder data from the email parser; UNKNOWN whether they do, so exclude by rule.
3. **`POST /api/crm/orders/:id/actions` `{action: "reprint" | "resend_app", actor}`** — **only if** a re-enqueue / re-push primitive already exists in `lib/` (see UNKNOWN). Reuse it; log to the existing activity/audit path; 409 if the order is cancelled. If no primitive exists, skip this endpoint, say so in the PR body, and add "M3 — order actions" to QUEUE.md as open.

Never guess a Zuppler hostname: if neither (a) nor (b) yields a URL, return `null` and say so in the PR body — Nick will paste a real order link and the template gets set in Vercel (STOP item for Nick, not for you).
5. **Contract:** document all of the above in `docs/crm-bridge-contract.md` with real response samples from the demo build, **and** add the missing entry for the existing `/api/crm/accounting/orders` (state plainly that its `restaurant_id` is bridge-id-only) — or, better, make that param go through `resolveRestaurantRef()` too and say so.
